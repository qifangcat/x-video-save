# Codex 与 GitHub 维护说明

本项目使用 Codex 修改和验证代码，用 Git 保存版本，用 GitHub 保存远端仓库与 Release 安装包。项目主页为 <https://github.com/qifangcat/x-video-save>。

## 日常修改

1. 在 Codex 中打开本项目，直接描述要修复的问题或新增的功能。
2. Codex 检查当前状态，保留已有修改，完成开发后检查差异并运行适当的测试或构建。
3. 适用检查通过后，Codex 默认提交本次任务相关的修改并推送到 GitHub，并汇报提交、验证结果及未验证事项。检查失败或存在冲突时先处理，不把失败写成通过。
4. GitHub 上每个提交都是一个可追溯的版本。推送源码本身不会自动发布新的 APK。

可以这样说：

> 修复视频下载进度显示，完成后测试并同步到 GitHub。

如果只想先看修改，可以说：

> 先修改和测试，暂时不要提交或推送。

## 发布安装包

需要新版 APK 时，明确告诉 Codex：“请发布新版本 APK”。递增 `app/build.gradle` 的 `versionCode`、更新 `versionName`，并新增与标签同名的 `release-notes/v版本号.md`，写明变更与真实验证范围。通过本地检查并推送源码后，推送对应的 `v版本号` 标签；GitHub Actions 会在云端运行画质选择测试、构建 APK，核对包名、版本与证书，再创建 Release 并上传 APK 和 SHA-256 文件。标签与版本不一致或缺少发布说明时不会发布。

云端使用仓库 Actions 加密密钥 `ANDROID_DEBUG_KEYSTORE_BASE64` 恢复 v0.1 的签名，APK 仍是 debug 构建。密钥不能提交到 Git、输出到日志或公开；签名证书指纹由工作流校验，确保能与现有签名兼容。不要覆盖既有标签或发布文件；发布后核对 Actions 结果、Release 下载和设备安装情况。GitHub 的 Actions 密钥可以供有权修改工作流的人使用，请限制仓库写权限。

## 出现问题时

先告诉 Codex 问题现象、设备和 X 版本，并要求查看版本历史及当前工作区。对于已经共享的错误提交，可在分析影响后用 `git revert` 生成撤销提交；不要随意改写远端历史。如果已发布 APK，代码回滚不会自动替换用户设备上的应用，也不会自动撤下或更新 Release，需要分别处理并验证安装兼容性。

可以这样说：

> 上次更新后下载失败，请查看提交记录并定位原因；先保留现有修改，修复或安全撤销问题提交，再验证并同步。

需要恢复旧文件而保留后续工作时，先说明想恢复的文件和目标版本，由 Codex 比较差异后选择处理方式。
